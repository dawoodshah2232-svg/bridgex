Trading platforms

Accounts, symbols and trade data — through adapters, not shortcuts.

Trading-platform adapters connect BridgeX to the venues your clients trade on: account and group synchronisation, symbol and session data, and trade feeds where the platform supports them. Connections are configured per server and per group, tested in a sandbox first, and every synchronisation run is logged so a mismatch can be investigated rather than guessed at.

Live trading-server access is enabled only with authorised broker credentials, broker approval and a tested sandbox run — never from the marketing site.

What the adapter handles

  • Account and group synchronisation
  • Symbol, session and schedule data
  • Trade and position feeds where supported
  • Funding requests routed to the right account

Adapter architecture

One model for every connection.

Adapters are the only way in or out. Nothing talks to a provider directly from a screen or a workflow — every call passes through an adapter that enforces the contract, logs the run and handles failure the same way.

01

One contract per category

Each provider category works to a defined adapter contract: what it sends, what it expects back, and what happens when either side fails. A new provider is a new adapter against that contract — not a new integration project from scratch.

02

Configuration, not custom code

Credentials, endpoints, routing rules and field mappings are configuration, held per tenant and per environment. Swapping a provider changes configuration — it does not rewrite your workflows.

03

Every run is logged

Synchronisation runs, webhook deliveries and API calls are recorded with their outcome. When something does not match, the log shows what was sent, what came back, and when — so a mismatch is investigated, not guessed at.

Events & webhooks

When delivery fails, nothing is lost.

Integrations fail — networks drop, providers go down, receivers are slow. The retry model treats failure as a normal event with a defined path, not as an emergency and never as silence.

  1. 01

    Event emitted

    A meaningful change — client verified, payment settled, commission approved — emits an event from the shared foundation.

  2. 02

    Delivered with a signature

    Webhooks carry a signature the receiver can verify, so a connected system knows the event genuinely came from BridgeX.

  3. 03

    Retried on failure

    If delivery fails, it is retried on a schedule with backoff. Each attempt is recorded — attempts, responses and timing.

  4. 04

    Dead-lettered, never lost

    After the retry schedule is exhausted, the event lands in a dead-letter queue with its full payload and error, for an operator to inspect and replay.

Idempotency is part of the contract: a retried delivery does not double-post a payment or duplicate a record. Financially material actions are designed to be safe to retry — because in production, they will be.

Honest limits

What we do not claim — and why it matters.

An integration page that lists logos is making promises on behalf of other companies' systems. We would rather describe the categories, the contracts and the testing — and let the demo prove the connection you actually need.

No named providers on this page

You will not find provider names or logos here — deliberately. An integration is only real once it has been configured and tested for a specific deployment, and a logo would claim otherwise.

No integration is 'live' until it is proven

Every connection goes through sandbox testing and reconciliation before it carries live records. Until that process passes, it is not presented as available.

Feasibility depends on the provider

Whether a specific provider can be connected depends on its own API, its terms and its test environment. We assess that during implementation and say so plainly if the answer is no.

Connections are assessed and built during implementation — see Integration & Migration — and the event and API model is part of the architecture.

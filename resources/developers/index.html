Versioning

Versioned from the first request

The API versions by URL: /v1, /v2, and so on. The version is part of the contract, not an afterthought bolted on after the first breaking change.

https://sandbox-api.example.bridgex.dev/v1/…

Example base URL for every sample on this page. The host is an example — it does not resolve, and the samples cannot be executed against it.

Example base URL — not a live endpoint

Additive changes stay in a version. New fields, new endpoints and new optional parameters arrive without breaking existing integrations. Clients that ignore unknown fields keep working — which is why we ask you to ignore unknown fields.

Breaking changes get a new version. Renamed fields, removed endpoints and changed semantics ship as /v2, with the previous version supported through a published deprecation notice period. No silent changes, ever.

v1 is planned, not live. The version number in these examples is a design decision, not a deployment. When the sandbox opens, this page will say so, and the samples will point at a host that answers.

Authentication

Planned, not specified

There are no real credentials, no token endpoint and no auth specification yet. This section describes the design direction only.

PlannedDesign direction — details with the sandbox
  • Scoped API keys issued per environment, so a sandbox key can never touch production data.
  • Tokens carry only the permissions their integration needs — least privilege, enforced server-side.
  • Keys are revocable per integration, with rotation that does not require downtime.
  • Every authenticated call is written to the audit trail, like every other action on the platform.

The samples below use Bearer EXAMPLE_TOKEN as a placeholder. It is not a credential and will never authenticate anything.

Webhooks

Events, delivered to you

The planned event catalogue covers the moments other systems need to know about. Delivery is designed around signed payloads, retries and idempotency — the boring parts that make webhooks trustworthy.

Limits & errors

Rate limits and errors, as designed

The limits below are the design targets for the sandbox, stated as plans — not enforced anywhere today, because there is nothing to enforce them on yet.

Rate limits (planned)

Per-key limits with clear headers on every response, so a client always knows how much budget remains. Exceeding a limit returns HTTP 429 with a retry-after hint — never a silent failure.

Errors (planned)

Every error carries a stable machine-readable code, a human-readable message and a link to the relevant docs section. 4xx errors mean the request was wrong; 5xx errors mean we were — and the message will say which.

SDKs (planned)

Client libraries are on the roadmap after the sandbox proves the API shape. Until then, the examples on this page are plain HTTP — any client, any language.
